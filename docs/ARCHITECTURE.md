# 项目架构概览

## 项目简介

本项目是一个面向 **Google Trends 相关搜索词增长监控** 的自动化数据采集与通知系统。它围绕一组可配置的基础关键词（seed keywords）定期查询 Google Trends 的相关查询数据，保存原始结果，生成汇总报表，并通过邮件或微信发送通知。

该系统适用于以下轻量级场景：

- 搜索趋势监控
- 新兴话题的早期信号发现
- 内容选题与 SEO 研究
- 长尾关键词挖掘
- 日报式研究工作流自动化

与通用型趋势分析平台不同，本仓库聚焦于一个明确而收敛的工作流：**采集相关查询、识别高增长项、持久化结果，并向操作者发送提醒**。

## 项目目标

本项目的设计目标包括：

- 以尽可能低的人工介入成本，周期性监控预定义关键词集合
- 基于可配置阈值识别高增长相关查询词
- 保存原始查询结果，便于复盘、排查与审计
- 生成结构化日报，供人工进一步分析
- 在不依赖复杂外部编排系统的前提下完成通知分发

## 非目标

当前实现并不试图提供以下能力：

- 基于数据库的历史时序存储
- 跨运行周期的告警去重
- 语义聚类、主题归一化或关键词清洗
- 趋势图表渲染或可视化看板
- 搜索引擎排名追踪
- 分布式调度或多工作节点执行
- 具备高可用、状态恢复与持久化保障的生产级任务调度平台

## 高层工作流

系统的单次运行流程可以概括为：

1. 从 `.env` 与 `config.py` 加载配置
2. 构建当前运行上下文
3. 针对每个基础关键词查询 Google Trends 相关搜索数据
4. 将每个关键词的原始结果保存为 JSON 文件
5. 将所有结果汇总生成每日 CSV 报表
6. 从 `rising` 数据中筛选高增长项
7. 发送一封每日报告通知
8. 按批次发送一封或多封高增长提醒通知

因此，本项目可以被视为一个适合运行在单机、轻量虚拟机或小型服务器上的监控服务。

## 项目实际监控的对象

一个非常重要、也最容易被误解的点是：本项目**并不是**在监控基础关键词本身的总体趋势分数。

对于每一个配置好的基础关键词，例如 `Music`、`Voice`、`Generator`，系统实际请求的是 Google Trends 提供的 **related queries（相关查询）** 数据，并重点关注其中两类结果：

- `top`：热门相关查询
- `rising`：增长中的相关查询

告警逻辑只基于 `rising` 数据集。当某条相关查询的数值超过配置阈值时，它才会被纳入“高增长提醒”。

因此，项目实际监控的是：

- **不是**基础关键词自身的趋势值
- **而是**围绕这些基础关键词出现的相关搜索词的增长情况

这一点对于正确理解 CSV 报告、邮件内容和最终提醒结果至关重要。

## 仓库模块说明

### `trends_monitor.py`

这是项目的主编排入口。

主要职责：

- 解析命令行参数
- 以测试模式执行一次，或以定时模式常驻运行
- 协调关键词批量采集流程
- 调用查询层获取 Google Trends 数据
- 生成每日汇总 CSV 报表
- 构建日报与高增长提醒邮件正文
- 调用通知层发送消息

其中的关键函数包括：

- `process_trends()`：执行一次完整的采集、汇总与通知流程
- `process_keywords_batch()`：处理一批基础关键词
- `generate_daily_report()`：生成标准化 CSV 汇总报表
- `build_daily_report_email()`：构建每日报告邮件正文
- `build_rising_alert_email()`：构建高增长提醒邮件正文
- `run_scheduler()`：维护进程内的日常调度循环

### `querytrends.py`

这是项目的数据采集层。

主要职责：

- 构建 `trendspy.Trends` 客户端
- 控制请求节奏与重试逻辑
- 支持代理访问
- 向 Google Trends 请求 related queries 数据
- 将原始结果序列化保存为 JSON 文件

关键实现特征包括：

- 同时使用全局请求限流器与显式休眠来降低访问频率
- 每次请求随机选择 User-Agent
- 在请求前清除 Cookie，以减少粘性追踪影响
- 在单个关键词层面做失败重试
- 支持项目代理和系统代理两类网络配置

### `notification.py`

这是项目的通知抽象层。

主要职责：

- 提供统一的 `send_notification()` 接口
- 通过 SMTP 发送 HTML 邮件
- 将 HTML 正文转换为适合微信发送的文本消息
- 自动拆分过长的微信消息
- 根据需要附带报表文件

当前支持的通知方式包括：

- `email`
- `wechat`
- `both`

### `wechat_utils.py`

这是微信登录与接收者管理模块。

主要职责：

- 管理 `itchat` 登录态与登录缓存
- 根据备注名、昵称、群名称或明确的用户 ID 查找接收者
- 向目标接收者发送文本消息和文件

该模块仅在启用微信通知时参与运行。

### `config.py`

这是项目的核心配置入口。

主要配置维度包括：

- 通知方式与接收对象
- SMTP 服务器与邮箱凭据
- 基础关键词集合
- Google Trends 查询参数（时间范围、地区）
- 请求节奏与批处理大小
- 定时执行时间
- 高增长阈值与告警分批大小
- 日志与输出文件命名

## 数据流说明

项目运行过程中涉及几类关键数据对象。

### 基础关键词集合

定义于 `config.py` 中，作为所有 Google Trends 查询的输入根集合。

### 相关查询结果

对于每个基础关键词，Google Trends 可能返回最多两组结果：

- `top`
- `rising`

当结果存在时，它们通常表现为 pandas `DataFrame`。

### 原始 JSON 文件

每个成功查询的基础关键词，都会生成一份独立的 JSON 文件，用于保留原始结果，便于后续审计、分析和调试。

### 汇总 CSV 报表

系统会将所有基础关键词返回的 `top` 和 `rising` 结果合并成一份结构化的 CSV 文件，作为当日汇总输出。

### 高增长提醒列表

这是运行过程中的一个内存数据结构，元素形态为：

- `(基础关键词, 相关查询词, 增长值)`

该列表只来自 `rising` 数据集，并且仅包含数值超过 `MONITOR_CONFIG['rising_threshold']` 的记录。

## 运行模式

### 测试模式

执行命令：

```bash
python trends_monitor.py --test
```

行为特征：

- 立即执行一次完整监控流程
- 可通过命令行传入临时关键词列表
- 执行完成后进程退出

该模式适用于调试、验证配置、人工试跑和一次性数据采集。

### 定时模式

执行命令：

```bash
python trends_monitor.py
```

行为特征：

- 在进程内部注册每日定时任务
- 进入循环等待，直到到达设定时间
- 每天执行一次 `process_trends()`
- 仅在当前 Python 进程持续存活时生效

需要特别说明的是：这并不是操作系统级的后台调度器。只要进程中断、退出或被 `Ctrl+C` 终止，调度行为就会停止。若需要更稳定的常驻运行方式，应由 `systemd`、`launchd`、Docker 重启策略或其他外部进程管理器来托管。

## 调度模型

调度能力基于 Python 的 `schedule` 库和一个常驻的进程内循环实现。

这意味着：

- 没有持久化任务状态
- 没有错过执行窗口后的补跑机制
- 没有任务队列
- `Ctrl+C` 一般会直接终止整个调度进程
- 第二天的执行前提是该 Python 进程仍然活着

项目还支持为调度时间附加一个随机延迟窗口，以降低执行时间过于固定带来的网络访问规律性。

## 请求策略与限流设计

本项目的请求策略明显偏向“稳定优先”，而不是“速度优先”。这是为了降低 Google Trends 触发限流、封锁或异常返回的风险。

整体策略由多个层次组成：

- 请求前增加随机等待
- 使用全局请求限流器控制分钟级与小时级频率
- 基础关键词之间增加额外等待
- 批次之间增加更长的冷却时间
- 出现错误后执行重试
- 在有条件时结合代理来改善访问稳定性

这意味着系统更适合低频、稳态的数据监控，不适合高吞吐的大规模采集任务。

## 代理支持

项目当前支持两类代理方式。

### 隧道代理

当环境变量中提供隧道地址和认证信息时，采集请求会通过指定隧道代理发出。

### 动态代理 API

当配置了代理 API 地址和账号信息时，系统会先向代理服务拉取一个代理地址，再据此构造后续请求使用的代理配置。

### 系统代理兜底

当项目自身未配置代理时，程序仍可能使用当前 shell 环境中注入的代理变量。对于 SOCKS 类型代理，代码会额外检查当前 Python 环境是否具备相应支持，以避免运行中出现隐性网络错误。

## 报告与通知语义

系统会发送两类通知，它们承担的职责不同。

### 每日报告

每日报告用于从运行级别总结本次监控结果，通常包括：

- 查询时间范围
- 查询地区
- 关键词总数
- 成功数与失败数
- 一份附带的 CSV 汇总文件

它的定位是“运行概览”和“日报归档”。

### 高增长提醒

高增长提醒是经过筛选后的信号通知，只包含超过阈值的 `rising` 项。

提醒内容通常包括：

- 基础关键词
- 相关查询词文本
- 增长值

为了避免单封邮件过长，提醒邮件会根据 `TRENDS_ALERT_BATCH_SIZE` 按批次拆分发送。

## 存储结构

项目运行后会按日期创建输出目录，目录名由配置项前缀与当天日期组成，例如：

```text
data_20260308/
```

其中通常包含：

- 每个关键词对应的原始 JSON 文件
- 当天生成的一份 CSV 汇总报表

日志输出则单独写入配置指定的日志文件中。

## 失败处理与容错方式

项目当前包含若干层防御性机制，但并不提供强事务保障。

已有的保护措施包括：

- 单关键词级别的重试逻辑
- 批处理级别的异常捕获
- 邮件发送阶段的 SMTP 异常处理与详细日志
- 微信通知阶段的重试机制
- 个别批次失败时尽量继续完成后续处理

当前已知的限制包括：

- 没有持久化失败队列
- 没有统一的补偿机制
- 没有“只发一次”的投递保障
- 没有跨多次运行的结果去重机制

因此，跨天重复提醒、同一主题再次出现等情况，在当前设计下都属于预期行为，而不是系统错误。

## 配置模型

项目采用“环境变量 + Python 默认配置”的双层配置结构。

典型可配置项包括：

- SMTP 主机、端口、传输安全模式与账号密码
- 通知渠道与接收对象
- Google Trends 查询地区与时间范围
- 监控关键词列表
- 请求频率控制参数
- 高增长判定阈值
- 每封提醒邮件的最大条目数
- 定时任务执行时间窗口

建议将 `.env` 视为部署环境配置层，将 `config.py` 视为项目默认配置层。这样更便于在不同机器或不同环境下复用同一套代码。

## 运行特征

### 优势

- 部署简单，依赖较轻
- 运行链路清晰，便于理解和修改
- 原始数据可追溯，利于排查问题
- 支持多种通知方式
- 请求节奏可配置，适合稳态运行

### 代价与取舍

- 当关键词集合较大时，整体运行时间会较长
- 定时调度强依赖进程存活，不是平台级服务
- 没有内建的告警抑制与去重机制
- 没有数据库存储历史结果
- 对 Google 返回质量、代理质量和 SMTP/微信可用性较为敏感

## 适用场景

本项目比较适合以下类型的工作流：

- 创业者或运营人员做趋势侦测
- 内容团队做选题挖掘
- SEO 团队做长尾机会发现
- 小规模研究任务的日常监控
- 单机环境下的低频搜索信号巡检

## 已知限制

在实际使用中，建议特别关注以下限制：

- Google Trends 的外部结果具有波动性，返回结构和内容可能随时间变化
- `rising` 的高百分比并不等于高绝对搜索量
- 过于宽泛的基础关键词可能带来较大噪声
- 当前实现可能在不同日期重复发送相似提醒
- 定时能力受限于 Python 进程生命周期
- 微信通知依赖有效且持续可用的登录状态

## 可扩展方向

当前架构为后续演进留下了较清晰的扩展空间，例如：

- 引入持久化状态以实现告警去重
- 增加 Dashboard 或 Web 界面
- 增加 Slack、Discord、Webhook 等通知通道
- 建立历史数据仓库存储与分析能力
- 支持规则化路由与更细粒度的告警策略
- 对关键词结果做语义归类和标准化
- 提供容器化部署与运维脚本

## 总结

从架构定位上看，本仓库更适合作为一个 **轻量级的 Google Trends 相关搜索词监控服务**，而不是一个完整的趋势分析平台。它的核心价值在于：将一组静态基础关键词，转化为一个可重复执行的发现式工作流，并将其中增长显著的相关搜索信号通过简单直接的渠道推送给操作者。

如果使用者需要的是一个透明、可读、易改造、低复杂度的监控工具，那么当前架构是足够清晰且具有良好可扩展性的：**查询、筛选、持久化、汇总、通知**。
